# Documentación Detallada del Proceso de Inicio de Sesión (Login)

Este documento explica, paso a paso, cómo viaja la información y qué componentes del sistema interactúan cuando un usuario inicia sesión en la aplicación RefaccionariaWeb.

## El Viaje del Inicio de Sesión: De la Vista al Servidor y de Regreso

### Paso 1: La Interfaz de Usuario (La Vista `Login.cshtml`)

*   **Ubicación:** `Views/Account/Login.cshtml`
*   **¿Qué es?** Es un archivo que combina HTML con código C# (Razor) para renderizar la página de inicio de sesión que el usuario ve en su navegador.

**¿Qué sucede aquí?**
1.  **El Formulario:** La vista contiene un formulario HTML (`<form>`) que apunta a la acción `Login` del `AccountController`. Esto se define con la etiqueta `<form asp-action="Login" method="post">`.
2.  **Los Campos de Entrada:**
    *   Hay campos de entrada para el correo electrónico y la contraseña: `<input asp-for="Email" />` y `<input asp-for="Password" />`.
    *   Los atributos `asp-for` son "Tag Helpers" de ASP.NET Core. Son muy importantes porque vinculan directamente estos campos HTML con las propiedades de una clase C# llamada `LoginViewModel`. Esto asegura que cuando el usuario envíe el formulario, los datos se empaqueten de forma ordenada.
3.  **El Botón de Envío:** Un botón (`<button type="submit">`) dentro del formulario que, al ser presionado, empaqueta los datos de los campos de entrada y los envía al servidor como una solicitud `HTTP POST`.

En resumen, la vista es la puerta de entrada. Su único trabajo es presentar el formulario y enviar los datos que el usuario ingresa al `AccountController`.

### Paso 2: El Contenedor de Datos (El `LoginViewModel`)

*   **Ubicación:** Es probable que esté en un archivo dentro de `Models/ViewModels` o en el archivo del controlador `AccountController.cs` si es una clase anidada, aunque por convención de Identity puede estar implícito.
*   **¿Qué es?** Es una clase C# muy simple que actúa como un "contenedor" o "paquete" de datos. No tiene lógica compleja.

**¿Qué sucede aquí?**
1.  **Definición de Propiedades:** Esta clase tiene propiedades que coinciden con los campos del formulario:
    ```csharp
    public class LoginViewModel
    {
        [Required]
        [EmailAddress]
        public string Email { get; set; }

        [Required]
        [DataType(DataType.Password)]
        public string Password { get; set; }

        [Display(Name = "Remember me?")]
        public bool RememberMe { get; set; }
    }
    ```
2.  **Transferencia de Datos:** Su único propósito es servir como un vehículo para transportar los datos del formulario (la Vista) al Controlador de una manera estructurada y fuertemente tipada.

### Paso 3: El Cerebro del Proceso (El `AccountController`)

*   **Ubicación:** `Controllers/AccountController.cs`
*   **¿Qué es?** Es el controlador que maneja todas las acciones relacionadas con las cuentas de usuario: registro, inicio de sesión, cierre de sesión, etc.

**¿Qué sucede aquí?**
1.  **Recepción de la Solicitud:** Cuando el usuario envía el formulario, la solicitud `HTTP POST` llega al método `Login` en este controlador. El método tiene una firma similar a esta:
    ```csharp
    [HttpPost]
    public async Task<IActionResult> Login(LoginViewModel model)
    ```
2.  **Model Binding:** ASP.NET Core realiza un proceso llamado "Model Binding". Automáticamente toma los datos que vienen en la solicitud (el email y la contraseña) y los usa para crear y rellenar una instancia del `LoginViewModel` (el parámetro `model`). ¡Todo esto ocurre antes de que se ejecute la primera línea de nuestro código en el método!
3.  **Inyección de Dependencias:** El `AccountController` tiene una dependencia de `SignInManager<IdentityUser>`. Esto significa que al inicio de la clase, verás algo como:
    ```csharp
    private readonly SignInManager<IdentityUser> _signInManager;

    public AccountController(SignInManager<IdentityUser> signInManager)
    {
        _signInManager = signInManager;
    }
    ```
    ASP.NET Core "inyecta" automáticamente una instancia de `SignInManager` en el controlador. Este `SignInManager` es una clase de ASP.NET Core Identity que contiene toda la lógica compleja para manejar el inicio de sesión.

### Paso 4: La Magia de la Autenticación (`SignInManager`)

*   **Ubicación:** Es parte del framework ASP.NET Core Identity, no un archivo que hayamos escrito directamente.
*   **¿Qué es?** Es el servicio de alto nivel que orquesta el proceso de autenticación.

**¿Qué sucede aquí?**
1.  **Llamada al Método `PasswordSignInAsync`:** Dentro del método `Login` del controlador, la línea más importante es:
    ```csharp
    var result = await _signInManager.PasswordSignInAsync(model.Email, model.Password, model.RememberMe, lockoutOnFailure: false);
    ```
2.  **Proceso Interno del `SignInManager`:** Este método realiza una serie de pasos críticos de seguridad:
    a. **Búsqueda de Usuario:** Utiliza otro servicio (`UserManager`) para buscar en la base de datos (tabla `AspNetUsers`) un usuario cuyo `Email` coincida con el `model.Email` proporcionado.
    b. **Verificación de Contraseña (¡La parte crucial!):**
        *   **NUNCA** compara contraseñas en texto plano.
        *   La contraseña que el usuario ingresó (`model.Password`) es procesada con un algoritmo de "hashing" criptográfico (el mismo que se usó cuando el usuario se registró).
        *   El resultado de este hash se compara con el hash de la contraseña que está almacenado en la base de datos para ese usuario.
        *   Si los hashes coinciden, la contraseña es correcta.
    c. **Comprobaciones Adicionales:** Verifica si la cuenta está bloqueada, si requiere confirmación por correo electrónico, etc.
3.  **El Resultado:** El método `PasswordSignInAsync` devuelve un objeto `SignInResult`.

### Paso 5: La Respuesta (Redirección y Cookies)

El `AccountController` ahora inspecciona el `result` del `SignInManager` y decide qué hacer.

**Caso A: Inicio de Sesión Exitoso (`result.Succeeded`)**
1.  **Creación de la Cookie de Autenticación:** Si el inicio de sesión fue exitoso, el `SignInManager` crea una **cookie de autenticación**. Esta es una pequeña pieza de información encriptada que contiene la identidad del usuario.
2.  **Envío al Navegador:** El servidor envía esta cookie al navegador del usuario como parte de la respuesta HTTP.
3.  **Almacenamiento en el Navegador:** El navegador guarda esta cookie. Si el usuario marcó "Remember me?", la cookie será persistente (durará varios días o semanas); si no, será una cookie de sesión (se borrará al cerrar el navegador).
4.  **Redirección:** El controlador redirige al usuario a la página de inicio o a la página que intentaba visitar antes de que se le pidiera iniciar sesión.
    ```csharp
    return RedirectToAction("Index", "Home");
    ```

**Caso B: Inicio de Sesión Fallido (`!result.Succeeded`)**
1.  **No se crea ninguna cookie.**
2.  **Añadir un Error:** El controlador añade un error al `ModelState`, que es un diccionario de errores del modelo.
    ```csharp
    ModelState.AddModelError(string.Empty, "Intento de inicio de sesión no válido.");
    ```
3.  **Devolver la Vista:** El controlador vuelve a mostrar la vista `Login.cshtml`.
    ```csharp
    return View(model);
    ```
    La vista `Login.cshtml` está configurada para mostrar los errores que haya en `ModelState`, por lo que el usuario verá el mensaje "Intento de inicio de sesión no válido" y podrá intentarlo de nuevo.

### Paso 6: Navegación Futura (El Usuario ya está Autenticado)

Una vez que el usuario ha iniciado sesión correctamente y tiene la cookie:

1.  **Envío de la Cookie:** En cada nueva solicitud que el navegador hace al servidor (por ejemplo, al hacer clic en "Mis Pedidos"), adjuntará automáticamente la cookie de autenticación.
2.  **Middleware de Autenticación:** El servidor tiene un "middleware" de autenticación que se ejecuta en cada solicitud. Este middleware inspecciona la solicitud en busca de la cookie de autenticación.
3.  **Validación y Desencriptación:** Si encuentra la cookie, la desencripta, valida su autenticidad y reconstruye la identidad del usuario (`ClaimsPrincipal`).
4.  **Establecimiento del `HttpContext.User`:** El middleware establece la propiedad `User` del contexto de la solicitud (`HttpContext.User`) con la identidad del usuario.
5.  **Disponibilidad en la Aplicación:** A partir de este punto, en el resto del procesamiento de la solicitud (controladores, vistas), la propiedad `User` está disponible y la aplicación "sabe" quién es el usuario. Esto permite:
    *   Que los atributos `[Authorize]` funcionen.
    *   Mostrar el nombre del usuario en la barra de navegación (usando `User.Identity.Name`).
    *   Filtrar datos para mostrar solo la información que pertenece a ese usuario.
